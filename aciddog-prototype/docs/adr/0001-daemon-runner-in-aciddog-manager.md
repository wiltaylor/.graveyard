# ADR-0001 — Local team supervision lives inside aciddog-manager

**Status:** Accepted
**Date:** 2026-05-03
**Deciders:** dev_lead, quality_consultant, security_consultant

## Context

The web UI must be able to start, stop, and manage `aciddog daemon` processes that run on the same host as the manager ("local teams"). The aciddog repository today has two crates: `aciddog` (orchestrator + TUI + headless daemon) and `aciddog-manager` (web portal). The manager is **excluded from the cargo workspace** because both crates link `sqlite3` transitively — `aciddog` via cozo's sqlite backend, `aciddog-manager` via sqlx-sqlite — and cargo refuses two packages linking the same native library in one resolver output (root `Cargo.toml:4-11`; confirmed: `Cargo.lock` shows cozo 0.7.6 pulls `sqlite` + `sqlite3-src`, and `aciddog-manager/Cargo.lock` shows `libsqlite3-sys`, both with `links = "sqlite3"`).

Three places the supervision logic could live:
1. A new `aciddog-supervisor` crate (separate process).
2. Inside `aciddog-manager` as a new subsystem.
3. Delegated to OS supervision (systemd-user units generated by the manager).

The manager today is a pure axum HTTP proxy + sqlite store — adding fork/exec child management is a posture change, not a continuation. Process management idioms in this repository today live in the `aciddog` core (`ai/codex_cli.rs`, `ai/claude_code.rs`, `ai/tools/bash.rs`, `repos/mod.rs`). The manager has no precedent.

## Decision

Put the subsystem inside `aciddog-manager` as a new `src/daemon_runner/` module that fork/execs the existing `aciddog daemon` CLI. The module is named `daemon_runner` — explicitly **not** `supervisor` — to avoid colliding with the existing per-agent / per-automaton `supervisor: bool` flag in WCL (`crates/aciddog/src/config.rs:90,218,1499,1511,2045`).

The manager is already a long-lived authenticated host process; it is the right trust and lifecycle owner. Crash isolation is preserved because the child is `exec`'d, not linked. Exposing process management through the existing auth/role/session machinery is cheaper than standing up a parallel surface in a sibling crate.

## Consequences

- Positive: no new sqlite-linking dance; no second auth surface; no second IPC; no extra deployment unit. Layering stays one-way (`manager → daemon`).
- Positive: spawning goes through the same CLI a human uses — no hidden API gets exercised only by the manager.
- Positive: `daemon_runner` as the module name keeps grep results unambiguous; "supervisor" stays attached to its WCL meaning.
- Negative: this is the manager's first child-process responsibility — operators who skim `aciddog-manager` looking for "axum + sqlite" will find more. Documented prominently in the crate's README and in this ADR.
- Negative: a manager crash leaves daemons orphaned. Mitigated by adoption-on-restart (ADR-0003).
- Negative: the manager binary now needs to know where to find `aciddog` on disk. Mitigated by an explicit `--aciddog-binary` CLI flag with `which("aciddog")` as the default.

## Alternatives Considered

- *Separate `aciddog-supervisor` crate.* Rejected: re-introduces the sqlite-linking problem if it persists state, doubles the auth surface, and there is no second client that needs the supervisor. Worth revisiting if a non-web UI ever wants to share supervision.
- *Linking `aciddog` as a library and calling `boot_orchestrator` in-process.* Rejected: blocked by the sqlite double-link, and removes crash isolation.
- *systemd-user units generated by the manager.* Rejected for v1: works only on Linux; requires writing into `~/.config/systemd/user/`; ties lifecycle observability to `systemctl` parsing; leaky on macOS / containers. May return as an opt-in `daemon_runner.backend = systemd` later.
